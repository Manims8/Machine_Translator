# Stage 3 implementation challenges

This log records issues observed while implementing and testing the local pipeline. The browser tests use the bundled ONNX models with external network requests blocked. A passing script check confirms execution and basic script selection, not translation quality.

## Unicode normalization and Indic controls

1. **Problem:** Canonically equivalent text can have different code-point sequences, and Indic join controls can affect rendering or spelling.
2. **Why:** Unicode permits composed and decomposed sequences; joiners are meaningful in several writing systems.
3. **Investigation:** Added NFC and tests for decomposed Latin input, Tamil/Kannada strings, and ZWJ/ZWNJ retention.
4. **Attempt:** Normalize with NFC only and reject unsupported C0/C1 controls instead of stripping broad character ranges.
5. **Outcome:** The component suite passed NFC composition, Indic text acceptance, and join-control preservation. NFKC and automatic spelling correction are not used.

## Sentence boundaries and model limits

1. **Problem:** Translating one long input risks exceeding a model's encoder positional limit; translating every short sentence independently can lose context.
2. **Why:** Input character length does not predict subword token count, and sentence boundaries inside decimals, URLs, or abbreviations are ambiguous.
3. **Investigation:** Used `Intl.Segmenter` with a fallback for protected inline periods, then counted candidate chunks with the selected local tokenizer, including both language tags.
4. **Attempt:** Keep adjacent sentences grouped until the actual `max_source_positions` boundary; split long sentences only at whitespace.
5. **Outcome:** The actual tokenizer test split 80 sentences into four chunks with counts 256, 256, 256, and 124 against the configured 256-token limit. Paragraph boundaries are rejoined separately. A single whitespace-delimited token longer than the model limit is not automatically split; the segmenter reports a safe failure before inference if protected text exceeds the limit.

## Placeholder preservation varies by model and marker form

1. **Problem:** Placeholder text can be dropped or changed by translation, so restoring values without validation could corrupt URLs, dates, identifiers, or terminology.
2. **Why:** The model tokenizers and model families segment and generate rare Latin marker strings differently. A generic marker probe does not prove a production marker form will survive.
3. **Investigation:** Ran actual browser inference for entity and glossary markers in all six directions, followed by entity protection/restoration and glossary phrase protection/restoration using the exact markers generated by the application.
4. **Attempt:** Validate each marker occurs exactly once and restore only after full validation. Maintain separate route gates for entities and glossary terms.
5. **Outcome:** The exact generated entity marker passed the full round trip for Kannada→English only. Entity values were modified for English→Tamil and Tamil→English despite some generic markers surviving. Glossary restoration failed for English→Tamil and English→Kannada: the model changed `ZXQGLOSSARY...` to `ZXQGLOSARY...`. Glossary protection remains disabled on every route; entries remain local references. Entity protection is enabled only for Kannada→English. Other routes warn and translate without marker insertion.

## Three model configurations behave differently

1. **Problem:** A behavior observed on one translation route cannot be assumed for all routes.
2. **Why:** English→Indic, Indic→English, and Indic→Indic use separate local model families and source tags; even within a family, source/target tags affect tokenization and generation.
3. **Investigation:** Executed six-direction browser regressions and per-route marker probes. `modelRouter.js` routes to English–Indic 200M, Indic–English 200M, or Indic–Indic 320M.
4. **Attempt:** Keep support flags per direction and per feature rather than enabling a feature by model family alone.
5. **Outcome:** All six translation smoke cases passed. Only Kannada→English entity protection passed the generated-marker round trip; no glossary route passed its integration check.

## Context and translation quality

1. **Problem:** Short independent calls can lose sentence context, but a whole long document can exceed source limits.
2. **Why:** Sentence splitting trades context for bounded input; languages also differ in morphology and word order.
3. **Investigation:** Group adjacent sentences and test chunk limits with the actual tokenizer; preserve paragraph order when reassembling.
4. **Attempt:** Translate grouped chunks, not every sentence separately, and retain an expandable diagnostic trace.
5. **Outcome:** The smoke suite verifies that every configured route returns text in the expected script. It does not establish semantic accuracy; sample outputs need human/native-speaker review for quality.

## Memory, latency, and offline operation

1. **Problem:** The application must avoid relying on downloads during inference and cannot keep unnecessary large model sessions active.
2. **Why:** Three pretrained ONNX families are served from local files and model loading is materially slower than a short translation.
3. **Investigation:** Ran browser smoke tests with external DNS and HTTPS blocked, checked external-origin requests, refreshed and translated again, and retained Stage 2 timing evidence separately.
4. **Attempt:** Continue using the existing lazy-loaded model lifecycle; expose load and inference times independently and avoid retraining or downloading models.
5. **Outcome:** The Stage 3 smoke run passed six routes and offline refresh with zero external origins requested. The production build succeeds with existing Transformers/Vite warnings about a runtime `new URL` and a large Transformers bundle; no change to model weights was needed.
